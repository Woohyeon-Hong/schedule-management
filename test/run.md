# 골든셋 검증

`./golden-events.json`의 시나리오 하나로 `docs/specs/`의 두 스펙을 실행하고, 결과를 스스로 점검해 보고한다. 기본은 1회 실행이다.

## 입력
- **시나리오**: `typical-day`(21개, 평범한 하루) / `empty-day`(0개) / `all-fixed-day`(고정 일정이 `workingHours`를 꽉 채운 날). 지정이 없으면 `typical-day`.
- **설정**: `config.json`이 없으면 `config.example.json`. `priorityRule`이 플레이스홀더 문장이면 `"마감이 급한 일을 먼저 배치한다"`로 놓는다.
- `_case`와 `_comment`는 주석이다. 이벤트 데이터로 취급하지 않는다.
- 캘린더 MCP를 호출하지 않는다. Slack으로 보내지 않는다.

## 실행
[decompose](../docs/specs/decompose.md)와 [arrange](../docs/specs/arrange.md)를 읽고 그대로 실행한다. 단 캘린더 조회 대신 위 시나리오의 이벤트 목록을 그날 이벤트로 쓴다.

출력 순서:
1. 이벤트별 판별 결과. 각 줄에 판별 로직 몇 번으로 정했는지 적는다. 2번이면 "옮기면 곤란한가"에 뭐라고 답했는지, 3번이면 왜 답이 서지 않았는지 한 줄로 쓴다
2. 유동 태스크의 분해 결과와 각 소요시간. 원본 설명의 어느 문구에서 나온 항목인지 함께 적는다. 설명이 없어 안 쪼갠 것은 그렇게 적는다
3. gap 목록(각 구간과 길이), gap 총합, 태스크 소요시간 총합, 초과분
4. Slack 리포트 전문

3번은 4번과 따로 낸다. 시나리오 때문에 비는 항목은 "해당 없음"으로 적는다 — `empty-day`는 1·2번과 3번의 태스크 쪽이, `all-fixed-day`는 gap이 0이다.

## 점검
출력끼리, 또 원본 이벤트와 대조하고 어긋난 것만 보고한다. 이상이 없으면 "이상 없음" 한 줄.

- **gap 산술** — 겹친 고정 일정을 합집합으로 처리했는지, `workingHours` 밖을 제외했는지, 구간 길이 합이 맞는지
- **누락** — 분해된 태스크 개수와 리포트에 등장하는 태스크 개수가 같은지. 초과분도 빠지지 않았는지
- **고정 시각** — 리포트의 시각이 원본 이벤트와 문자 그대로 같은지

## 스펙 미정의 신고
스펙이 답을 주지 않는 상황을 만나면 **임의로 정하지 말고** 그 지점을 보고한다. 어쩔 수 없이 하나를 골라 진행했다면 무엇을 골랐는지 함께 적는다.

## priorityRule 검증 (선택)
배치 기준이 실제로 작동하는지 확인할 때만 한다. 아래 두 문장으로 각각 한 번씩 더 돌리고 **태스크 순서만** 비교해 보고한다 — 판별·분해·리포트는 다시 출력하지 않는다.

```
"마감이 급한 일을 먼저 배치한다"
"오전에 집중력이 필요한 일을 먼저 배치하고, 오후로 갈수록 가벼운 일을 배치한다"
```

두 순서가 같으면 `priorityRule`이 무시되고 있는 것이므로 보고한다. `typical-day`에는 마감이 명시된 태스크가 둘(e3 다음주 화요일, e17 오늘 18시) 있어 첫 기준으로도 순서가 결정된다. `empty-day`는 태스크가 없어 건너뛴다.

# Spec: 배치(Arrange) 엔진

관련 문서: [decompose](./decompose.md) — 이 문서는 그 출력을 입력으로 받는다

## Objective
쪼개기(decompose) 단계가 만든 항목들(`kind: fixed | task`)을 받아, 유동 태스크(`task`)들을 효율적인 순서로 배치한다. 고정 일정(`fixed`)은 움직이지 않는다 — 그 사이사이 빈 시간에 유동 태스크를 채워 넣는 문제다.

성공은 decompose와 동일한 기준이다: "사용자가 리포트를 보고 실제로 그대로 따르는가."

## 실행 방식
decompose와 마찬가지로 커스텀 코드 없음. `schedule` 루틴이 decompose 추론 직후, 같은 세션 안에서 이어서 수행하는 **두 번째 추론 단계**다. 별도 함수 호출이 아니라 하나의 프롬프트 흐름 안에서 "먼저 판별·분해하고, 그 다음 아래 배치 로직에 따라 순서를 정하라"는 지시로 존재한다.

배치 기준(우선순위 로직)은 스펙에 하드코딩하지 않는다 — 사람마다 다르기 때문이다. 대신 `config.json`의 `priorityRule` 필드(자유 텍스트)에 사용자가 자기 기준을 직접 적어두고, 루틴이 그 문장을 그대로 배치 지시문에 포함시킨다.

## Project Structure


## config.json 추가 필드
```json
{
  "priorityRule": "본인이 원하는 배치 기준을 자연어로 서술 (예: \"오전에 집중력이 필요한 일을 먼저 배치하고, 오후로 갈수록 가벼운 일을 배치한다\" 또는 \"마감이 급한 일을 무조건 먼저 배치한다\")",
  "onOverflow": "push"
}
```
- `priorityRule`: 유동 태스크들의 순서를 정하는 기준. 사용자마다 다르게 채운다 — 배치 전략을 코드나 스펙에 고정하지 않고 이 문장 하나로 위임한다.
- `onOverflow`: 하루 안에 다 못 들어가는 태스크가 생겼을 때 처리 방식. `"push"`(기본) 또는 `"flag"`.

## 배치 로직
1. 고정 일정(`fixed`)들을 실제 시각 순서대로 나열해 하루를 여러 개의 빈 시간(gap)으로 나눈다.
2. 유동 태스크(`task`)들의 전체 순서를 `config.json`의 `priorityRule`에 따라 정한다.
3. 정해진 순서대로 앞의 gap부터 채운다 — 한 gap에 들어갈 수 있는 만큼(`estimatedMinutes` 합이 그 gap 길이를 넘지 않는 선까지) 넣고, 넘치면 다음 gap으로 넘긴다.
4. 하루의 모든 gap을 다 채우고도 남는 태스크가 있으면(=하루 총 유동 시간이 부족) `onOverflow`에 따라 처리한다:
   - `"push"`: 별도 표시 없이 순서 리스트 맨 뒤에 그대로 이어서 보여준다. 사용자가 순서를 보고 오늘 다 못 끝낼 수도 있다는 걸 스스로 판단한다.
   - `"flag"`: 오늘 남은 gap에 들어가지 않는 지점부터 구분선을 넣어 "여기부터는 오늘 안 들어갈 수도 있음"을 표시한다.
5. 다음날로 자동으로 넘기거나, 캘린더에 다시 등록하는 것은 하지 않는다 (범위 밖 — 캘린더 쓰기는 이번 단계에서 하지 않는다).

## 출력 형태 (Slack 리포트)
- 고정 일정은 **실제 캘린더 시각**을 그대로 보여준다 (이건 추정이 아니라 사실이므로).
- 유동 태스크는 **순서 번호 + 예상 소요시간만** 보여주고 구체적 시각은 적지 않는다 — 소요시간 추정은 틀릴 수 있는데, 틀린 시각을 보여주면 신뢰만 깎이고 순서/소요시간 정보로도 유용성은 유지되기 때문이다.

예시:
```
[오늘 하루 계획]

09:00-09:30 팀 주간 회의 (고정)

  1) 3분기 실적 데이터 정리 (45분)
  2) 보고서 초안 작성 (60분)

10:30-11:00 코드 리뷰 PR #482 (고정)

  3) PR #485 리뷰 (20분)
  4) 이메일 회신 (15분)
```

## Testing Strategy
코드가 없으므로 전부 골든셋 수동 리뷰다. [decompose](./decompose.md)의 골든셋 실행 결과(판별·분해된 항목들)를 입력으로 받아, 이 배치 로직을 이어서 실행하고 사람이 순서가 말이 되는지 리뷰한다. `priorityRule`을 몇 가지 다른 문장으로 바꿔가며 돌려보고, 실제로 그 기준대로 순서가 바뀌는지 확인한다.

## Boundaries
- **Always**: 고정 일정 시각은 절대 바꾸지 않음, `config.json` 커밋 금지, 유동 태스크에 가짜 시각을 지어내지 않음
- **Ask first**: `priorityRule`/`onOverflow` 외에 새로운 배치 설정 필드 추가, 출력 형태(리포트 포맷) 변경
- **Never**: 캘린더에 실제로 쓰기(수정·재배치) API 호출, 다음날 일정을 자동으로 건드리는 것

## Success Criteria
- 고정 일정은 항상 원래 시각 그대로 표시됨
- `priorityRule`을 다르게 설정하면 골든셋에서 순서가 실제로 다르게 나옴 (배치 기준이 장식이 아니라 실제로 작동함)
- 하루 총 유동 시간이 부족한 골든셋 케이스에서 `onOverflow: push`가 순서 리스트 끝에 자연스럽게 이어짐 (누락되지 않음)
- 사용자가 리포트만 보고 "이 순서대로 하면 되겠다"고 납득함

## Open Questions
- 한 유동 태스크가 어느 gap에도 통째로 들어가지 않을 만큼 클 때(예: 90분 태스크, 남은 gap은 60분) 쪼개서 걸치게 할지, 다음 gap으로 통째로 미룰지 — 골든셋으로 실제 이런 케이스가 나오면 결정
- `priorityRule`이 서로 모순되는 여러 기준을 담고 있을 때(예: "마감 급한 거 먼저, 근데 아침엔 집중 작업만") 우선순위가 꼬일 수 있음 — 사용자가 문장을 다듬는 것으로 해결할지, 아니면 이 스펙에서 기준 간 우선순위 규칙을 추가할지

# Spec: 쪼개기(Decompose) 엔진

관련 문서: [daily-decompose-report](../ideas/daily-decompose-report.md) · 배치(Arrange) 스펙은 별도 문서로 분리 예정 (`arrange.md`, 아직 미작성)

## Objective
그날의 Google Calendar 이벤트를 입력받아, (1) 고정 일정인지 쪼갤 대상(유동 태스크)인지 판별하고, (2) 유동 태스크는 실행 가능한 최소 논리 단위로 분해하며, (3) 각 단위의 예상 소요시간을 추정한다. 배치(순서 재배치)는 다루지 않는다 — 이 판단 결과는 배치 단계의 입력이 된다.

성공은 "출력이 사용자 본인이 보기에 말이 되는가"로 판단한다: 고정 일정을 잘못 쪼개지 않고, 유동 태스크가 실제로 하나씩 처리 가능한 단위로 나뉘어 있으면 된다.

## 실행 방식
**커스텀 코드 없음.** 이 로직은 `schedule` 스킬(크론)로 등록된 Claude Code 루틴이 매일 지정 시각에 실행하는 **하나의 프롬프트 지시문**으로 존재한다. 별도 서버, 별도 스크립트, Anthropic API를 직접 호출하는 코드가 필요 없다 — 루틴 자체가 Claude 에이전트이므로 판별/분해 추론을 코드 없이 직접 수행한다.

루틴이 매 실행마다 하는 일:
1. 이 저장소의 `config.json`을 `Read` 툴로 읽어 개인 값(캘린더 ID, Slack 채널, 리포트 시각 등)을 확인한다.
2. Google Calendar MCP(`list_events`, read-only)로 그날 이벤트를 조회한다.
3. 아래 "판별 로직"·"분해 로직"에 따라 각 이벤트를 분류·분해·소요시간 추정한다.
4. 결과를 (나중에 작성할) 배치 스펙이 정의하는 다음 단계로 넘긴다.

검증 단계에서는 2번 대신 `fixtures/golden-events.json`을 `Read`로 읽어 목 데이터로 대체한다 (아직 의미 있는 실제 일정이 없으므로).

## Project Structure
```
config.example.json    # 공유 템플릿
config.json             # 개인 값 (커밋 금지)
fixtures/
  golden-events.json    # 목 캘린더 이벤트 (검증용)
docs/specs/decompose.md # 이 문서 — 실질적으로 루틴의 스펙이자 프롬프트 원본
```
소스 코드 디렉터리는 없다. 이 문서의 "판별 로직"·"분해 로직"·"출력 형태" 절이 스케줄 루틴 프롬프트에 그대로 들어간다.

## 출력 형태 (배치 단계와의 계약)
루틴은 각 캘린더 이벤트를 아래 항목들의 리스트로 변환해서 다음 단계(배치)에 넘긴다. 코드 타입은 아니지만, 필드 구성은 고정한다:

- `id`: `${원본 이벤트 id}:${순번}`
- `sourceEventId`: 원본 캘린더 이벤트 id
- `title`: 실행 가능한 한 문장 (예: "보고서 초안 목차 작성")
- `kind`: `fixed` 또는 `task`
- `estimatedMinutes`: 예상 소요시간(분)

- `kind: fixed` 항목은 분해되지 않고 원본 이벤트 그대로 1개 항목이 된다 (`estimatedMinutes`는 실제 이벤트 길이).
- `kind: task` 항목은 원본 이벤트 하나가 N개로 분해될 수 있다. 분해 기준은 시간이 아니라 **의미 단위**(더 쪼개면 의미가 없어지는 논리적 최소 작업)다 — `estimatedMinutes`는 분해 결과에 따라오는 부산물이지, 분해 기준 자체가 아니다.
- 분해된 항목들의 `estimatedMinutes` 합이 원본 이벤트 길이를 넘거나 못 미쳐도 이 단계는 신경 쓰지 않는다 — 하루 전체 시간에 맞추는 건 배치 단계의 책임이다.

## 판별 로직 (고정 vs 유동)
1. **컨벤션 우선**: 이벤트 제목이 `[TASK]` 프리픽스로 시작하면 무조건 유동 태스크로 취급. 향후 `[FIXED]` 같은 반대 컨벤션도 동일한 우선순위로 추가 가능.
2. **컨벤션이 없으면 판단**: 제목/설명을 보고 "이건 정해진 시간에 참여해야 하는 일(회의, 예약, 통화 등)인가, 아니면 사용자가 알아서 처리하면 되는 작업인가"를 분류. 대표 키워드(회의/미팅/예약/통화/면접 → 고정, 작성/정리/준비/리뷰/기획 → 유동)를 참고한다.
3. 애매하면 **고정으로 분류** (기본값을 보수적으로 — 잘못 쪼개는 것이 안 쪼개는 것보다 사용자 신뢰를 더 크게 깎는다).

## 분해 로직 (유동 태스크 → 실행 단위)
- 입력: 이벤트 제목 + 설명(있으면)
- 출력: 실행 가능한 문장 단위 리스트. "실행 가능하다"의 기준: 사용자가 그 문장만 보고 바로 무엇을 해야 할지 알 수 있어야 한다 (예: "프로젝트 A 작업" → "프로젝트 A 기획서 초안 작성", "프로젝트 A 팀원 피드백 반영" 등).
- 설명이 텅 비어 제목만으로 분해 재료가 부족하면, **분해하지 않고 원본 그대로 1개 항목(`kind: task`)으로 반환**한다 — 억지로 쪼개지 않는다.
- 각 단위에 대해 별도로 예상 소요시간(분 단위)을 추정한다. 과거 실측 데이터 기반 보정은 하지 않는다 (범위 밖 — [daily-decompose-report](../ideas/daily-decompose-report.md)의 Not Doing 참고).

## Testing Strategy
코드가 없으므로 자동화된 유닛 테스트 대상도 없다. 검증은 전부 **골든셋 수동 리뷰**로 한다:
- `fixtures/golden-events.json`(목 캘린더 이벤트 15개, 고정/유동/애매함/컨벤션/빈 설명 케이스 포함)을 스케줄 루틴과 같은 프롬프트로 돌려본다.
- 사람이 직접 "이 판별/분해가 말이 되는가"를 리뷰한다 (LLM 출력은 매번 달라질 수 있어 strict assert가 아니라 정성 평가).
- [daily-decompose-report](../ideas/daily-decompose-report.md)의 "Key Assumptions to Validate" 1번(제목만으로 의미있게 쪼갤 수 있는가)을 이 골든셋으로 검증한다.

## Boundaries
- **Always**: 캘린더에 read-only 스코프만 사용 (쓰기 API 호출 금지), `config.json` 커밋 금지, 출력 형태를 바꾸면 이 문서와 배치 스펙을 함께 갱신
- **Ask first**: 판별/분해 기준(프롬프트 지시문) 핵심 변경(정확도에 큰 영향), 스케줄 실행 시각/트리거 변경
- **Never**: 개인 설정값을 문서나 프롬프트에 하드코딩, 캘린더 이벤트 수정·삭제 API 호출

## Success Criteria
- 골든셋 15개 이벤트에 대해 명백한 오탐(고정 일정을 유동으로 분류하거나 그 반대) 없음
- 유동 태스크로 분류된 이벤트가 실행 가능한 단위로 분해됨 (사람이 보고 "이거 하나만 봐도 뭘 할지 알겠다"고 판단)
- 모든 출력이 정의된 필드 구성(`id`/`sourceEventId`/`title`/`kind`/`estimatedMinutes`)을 항상 포함
- `config.example.json`만 보고 지인이 자기 `config.json`을 채워 자기 `schedule` 루틴을 등록할 수 있음

## Open Questions
- 지인 배포 시 Google OAuth(캘린더 read 권한) 인증 플로우를 어떻게 안내할지 (셀프서브 가이드 필요 여부) — [daily-decompose-report](../ideas/daily-decompose-report.md)에서 이미 제기된 질문, 여기서도 동일하게 적용됨
- `[TASK]` 외에 추가 컨벤션(캘린더 색상, `extendedProperties` 등)을 지원할지는 실제 사용해보면서 필요성이 확인되면 추가
- `schedule` 스킬 루틴에서 `config.json` 값을 프롬프트 지시문에 어떻게 자연스럽게 엮을지(매 실행마다 `Read`로 불러오게 지시하는 문구 설계)는 실제 루틴 작성 시 확정

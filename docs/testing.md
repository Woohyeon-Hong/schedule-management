# 골든셋으로 검증하기

루틴에는 코드가 없다. 로직은 `docs/specs/`의 프롬프트뿐이고 LLM 출력은 매번 조금씩 달라지므로, 검증은 **골든셋을 돌려보고 사람이 읽는 것**으로 한다. 자동화된 통과/실패 판정은 없다.

## 시나리오

`fixtures/golden-events.json`에 세 개가 들어 있다.

- **`typical-day`** (21개) — 평범한 하루. 고정/유동/애매/컨벤션/빈 설명 + 종일 일정, 겹친 고정 일정, `workingHours` 경계에 걸친 일정, gap보다 큰 태스크, 마감 2건, 컨벤션 vs 키워드 충돌
- **`empty-day`** (0개) — 일정이 없는 날
- **`all-fixed-day`** (2개) — 고정 일정이 `workingHours`를 꽉 채워 gap이 0인 날

## 실행

Claude Code에서 이 저장소를 열고 아래를 그대로 준다. `<시나리오>`와 `<배치 기준>`만 바꾼다.

```
docs/specs/decompose.md와 docs/specs/arrange.md를 읽고, 두 스펙을 그대로 실행해줘.

단 캘린더는 조회하지 말고 fixtures/golden-events.json의 "<시나리오>" 배열을
그날 이벤트로 써. _case와 _comment는 사람이 읽는 주석이니 이벤트 데이터가 아니야.
config.json이 없으면 config.example.json 값을 쓰되,
priorityRule은 "<배치 기준>"으로 놓고. Slack으로는 보내지 마.

결과를 이 순서로 보여줘.
  1. 각 이벤트를 고정/유동 중 무엇으로 판별했는지, 근거 한 줄씩
  2. 유동 태스크를 어떻게 쪼갰고 소요시간을 얼마로 봤는지
  3. workingHours에서 고정 일정을 뺀 gap 목록과 각 길이, 태스크 소요시간 총합
  4. 완성된 Slack 리포트 전문
```

3번을 따로 시키는 이유: gap 산술이 틀리면 배치 전체가 틀리는데, 리포트만 보면 틀린 걸 알 수 없다. 숫자를 꺼내놓게 해야 검산할 수 있다.

## 사람이 볼 것

- **판별** — 고정을 유동으로, 유동을 고정으로 분류한 게 있는가. 애매한 것(점심, 헬스장)이 고정으로 갔는가
- **분해** — 각 항목이 "이거 하나만 봐도 뭘 할지 알겠다" 수준인가. 설명이 없는 이벤트를 억지로 쪼개지 않았는가
- **gap 산술** — 겹친 고정 일정을 합집합으로 처리했는가. `workingHours` 밖은 뺐는가
- **누락** — 쪼갠 태스크가 리포트에 전부 있는가. 초과분도 빠지지 않았는가
- **고정 시각** — 원본 캘린더 시각 그대로인가
- **리포트** — 이대로 하루를 살 수 있겠는가

## `priorityRule`이 장식이 아닌지 확인

같은 시나리오를 배치 기준만 바꿔 두 번 돌리고 순서를 비교한다. 순서가 그대로면 `priorityRule`이 무시되고 있는 것이다.

```
"마감이 급한 일을 먼저 배치한다"
"오전에 집중력이 필요한 일을 먼저 배치하고, 오후로 갈수록 가벼운 일을 배치한다"
```

`typical-day`에는 마감이 명시된 태스크가 둘(e3 다음주 화요일, e17 오늘 18시) 있어 첫 번째 기준으로도 순서가 결정된다.

## 알려진 미해결

`typical-day`는 현재 스펙으로 답이 안 나오는 케이스를 일부러 포함한다. 아래는 검증 실패가 아니라 **스펙의 구멍**이다 — 자세한 건 `docs/ideas/project-notes.md`의 Open Questions.

- 종일 일정(e16)을 고정으로 보면 하루 전체가 막힌다. 리포트에 어떻게 표기할지도 정해져 있지 않다
- 180분짜리 태스크(e20)는 어느 gap에도 통째로 안 들어간다
- gap에 다음 순서 태스크가 안 들어갈 때 건너뛰어도 되는지 정해져 있지 않다 — 순서를 엄수하면 `typical-day`에서 gap 285분 중 110분이 빈다
